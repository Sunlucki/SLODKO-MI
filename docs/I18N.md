# Languages and translations

The site is published in Polish (default, at `/`) and in English, Russian and Ukrainian (`/en/`, `/ru/`, `/uk/`). The
Polish files in `src/data/` are the only source of **structure and facts**; a translation is a **text-only overlay** in
`src/data/i18n/<locale>/` that replaces strings of the Polish content. Code: `src/content/i18n.ts` (rules),
`src/content/validate.ts` (merge + `translationStatus()`), `src/content/index.ts` (runtime).

## How an overlay works

```
src/data/site.json                  ← Polish: texts + structure + settings
src/data/products.json
src/data/pages/home.json
src/data/pages/polityka-prywatnosci.json
src/data/i18n/en/site.json          ← English: ONLY the texts, at the same key paths
src/data/i18n/en/products.json
src/data/i18n/en/pages/home.json    ← same file name as the Polish page
src/data/i18n/ru/…  src/data/i18n/uk/…
```

At build time (and in `npm run dev`) every overlay is merged onto a copy of the validated Polish content; the merged
result must pass the same schema. The site then has one complete content object per language. Consequences:

- Change the structure once (section order, a new product, a link, a price, an image, hours) in the Polish file — every
  language follows automatically.
- A text that a translation does not provide is shown **in Polish** on that language's pages (never an error).
- A translation can never add sections, products, links or settings.
- A missing translation file is the same as an empty one.

## Matching rules

| In the Polish file | In the overlay | Example |
| --- | --- | --- |
| Object | Only keys that exist in the Polish object (unknown key = error) | `{ "seo": { "title": "…" } }` |
| String | Replaced by the overlay string (must be non-empty if the field is required) | `"tagline": "HEY, cinnamon roll time"` |
| Array of objects that all have `id` (sections), `slug` (products, categories) or `date` (`specialHours`) | Items matched **by that key**; each overlay item must contain its `id`/`slug`/`date`; order in the overlay does not matter; items can be left out | `{ "sections": [{ "id": "faq", "heading": "Questions" }] }` |
| Any other array (headline lines, `body` paragraphs, FAQ `items`, `nav`, `footer.columns`, `images`, `ticker`, `blocks`…) | Matched **by position**: overlay item 0 → Polish item 0; shorter overlay = the rest stays Polish; longer overlay = error | `"nav": [{ "label": "Flavours" }, { "label": "About" }]` |
| Number, `true`/`false` | Not allowed (they are settings); `null` anywhere = keep the Polish value | — |

Leave out every key you do not translate — `href`, `src`, `type`, `variant`… An identical copy of a technical string or
number is tolerated (that is how `id`/`slug`/`date` stay in keyed items); a different value is an error, and so is a
changed value inside a settings subtree (`links`, `theme`, …). Inside a positional array keep the Polish order: to translate only
the third FAQ item, the first two must be present — `{}` for an object you skip, `null` for a string you skip (both stay
Polish).

### Example — `src/data/i18n/en/site.json`

```json
{
  "tagline": "HEY, it's cinnamon roll time",
  "address": { "entranceNote": "Entrance from ul. Hetmańska" },
  "nav": [{ "label": "Flavours" }, { "label": "About us" }, { "label": "Reviews" }, { "label": "Getting here" }],
  "header": { "cta": { "label": "Order on Wolt" } },
  "specialHours": [{ "date": "2026-10-29", "note": "Opening later than usual" }],
  "ui": { "product": { "allergensHeading": "Allergens" }, "reviews": { "countForms": ["review", "reviews", "reviews"] } }
}
```

### Example — `src/data/i18n/en/products.json`

```json
{
  "categories": [{ "slug": "cynamonki", "name": "Cinnamon rolls" }],
  "products": [
    {
      "slug": "oreo",
      "name": "Oreo",
      "shortDescription": "Oreo cream, crushed cookies and milk chocolate.",
      "images": [{ "alt": "Oreo cinnamon roll with cream and crushed Oreo cookies" }],
      "seo": { "title": "Oreo cinnamon roll – Poznań" }
    }
  ]
}
```

### Example — `src/data/i18n/en/pages/home.json`

```json
{
  "seo": { "title": "Cinnamon rolls in Poznań, Wilda", "description": "…" },
  "sections": [
    { "id": "start", "headline": [{ "text": "HEY, POZNAŃ…" }, { "text": "IT'S" }, { "text": "ROLL TIME" }] },
    { "id": "faq", "heading": "Questions & answers.", "items": [{ "question": "Where exactly are you?", "answer": "…" }] }
  ]
}
```

(`path` is not translated: the English home page is `/en/`, the privacy page `/en/polityka-prywatnosci/`.)

## What is never translated

Defined in `src/content/i18n.ts`:

- **Keys** `NOT_TRANSLATABLE`: `$schema`, `id`, `slug`, `type`, `kind`, `mode`, `href`, `src`, `path`, `url`, `category`,
  `slugs`, `productSlugs`, `variant`, `tone`, `date`, `opens`, `closes`, `days`, `postalCode`, `country`, `currency`,
  `unit`, `ogImage`, `publishTime`, `fetchedAt`, `code`, `htmlLang`, `ogLocale`, `defaultLocale`, `fallbackLocale`,
  `policyHref`, `legalName`, `wordmark` — wherever they occur; a list under such a key (`productSlugs`, `slugs`) is
  technical item by item.
- **Settings subtrees** (`SETTINGS`), only at these places: `site.json` → `links`, `theme`, `i18n`, `hours`, `contact`,
  `address.geo`; `products.json` → `products[…].allergens`; pages → `sections[…].source`. The same names elsewhere are
  texts: `ui.visit.hours`, `ui.visit.phone` and the footer `links[].label` are translated as usual. Allergen *display
  names* are texts in `ui.allergenNames`.
- **Numbers and booleans** anywhere (prices, `enabled`, `featured`, `aiGenerated`, `maxItems`…).
- **`reviews.json`**: reviews are shown in the author's original words on every language version.

Everything else that is a string is a text — the `i18n` column of the generated tables in
[CONTENT-REFERENCE.md](CONTENT-REFERENCE.md#field-reference-generated) says `yes` for each translatable field. Note that
some texts are deliberately translatable although they are names: `site.name`, product `name`, `address.city`,
`address.street` — keep Polish street and brand names (see [style](#translation-style)).

## Status and checks

| Command | What it tells you |
| --- | --- |
| `npm run i18n:status` | Table per language and file: translated / total texts, % and missing count. Exit 0 |
| `npm run i18n:status -- en --missing` | Also lists every missing text of English: path in the file → Polish text |
| `npm run i18n:check` | Same as status, exits 1 while any language misses texts |
| `npm run content:check` | Validates overlays: unknown keys, technical values, unmatched `id`/`slug`/`date`, too many array items, empty required texts, folders of unknown languages, page overlays without a Polish page |

Paths in the missing list look like `sections[id=faq].items[2].answer`, `products[slug=oreo].images[0].alt` or
`specialHours[date=2026-10-31].note`: `[id=…]`/`[slug=…]`/`[date=…]` is the item with that key, `[2]` the third item of a positional array — so
they map directly onto the overlay file. The MCP tool `translation_status` and `npm run ai` with a translation
instruction use the same report.

**Limits of the status:** it reports texts that are *missing*, not texts that are *outdated*. When a Polish text changes,
its old translation stays in place and is still counted as translated — update or delete it in the same change.

## Everyday workflows

**Translate everything that is missing.** `npm run i18n:status -- en --missing`, then add each text at its path in
`src/data/i18n/en/…`; run `npm run content:check`; repeat for `ru`, `uk`. With an LLM: `npm run ai -- "Przetłumacz
brakujące teksty na angielski"` (it receives the missing list and the keyword map), or in an MCP chat: "translate the
missing English texts". Check the result with `npm run i18n:status`.

**A Polish text changed.** Change the same path in every overlay (`en`, `ru`, `uk`) in the same edit, or delete the
overlay entry so that `i18n:status` lists it as missing. Search: `grep -rn "old phrase" src/data`.

**A section was added.** Nothing breaks: its texts show in Polish and appear in `i18n:status`. Add an item with its `id`
to `sections` of each overlay.

**A section was moved.** Nothing to do — sections are matched by `id`.

**A section was deleted or its `id` renamed.** Remove/rename the item in every overlay — otherwise `content:check` fails
with `sections: item "<id>" does not exist in the default language`.

**A positional array changed** (FAQ item inserted in the middle, nav link added, image added to a gallery). Positions after the change shift: re-align the overlay arrays in the same edit (insert `{}` or
the translation at the same index, remove the deleted index). If you forget, translations land on the wrong items
without any error. Appending at the end is safe (the new item just shows in Polish).

**A product was added or a slug renamed.** Add/rename the item by `slug` in every `products.json` overlay.

**A page was added.** Create `src/data/i18n/<locale>/pages/<same-name>.json` for each language (or leave it: the page
then shows in Polish under `/en/<path>/`). Deleting a page: delete its overlays too (the MCP `delete_page` tool and
`npm run ai` do this automatically).

## What the visitor gets

- **Routes:** every page and product exists in every language: `/`, `/produkt/oreo/`, `/en/`, `/en/produkt/oreo/`,
  `/ru/polityka-prywatnosci/`… (`src/routes.tsx`). Paths and slugs stay Polish in all languages.
- **Content:** components call `useContent()`, which returns the merged content of the page's language
  (`localeFromPath()` reads the URL prefix). Prices, dates, plural forms and numbers are formatted with `Intl` in that
  language (`locales[].htmlLang`).
- **Links:** internal links from content get the page's prefix automatically (`SmartLink` → `resolveHref` →
  `c.localize()`); the build fails if a page links to another language version (except the language switcher).
- **Language switcher:** round button in the header (native `<details>`, works before JS), list in the menu and the
  footer. Plain links to the same page in the other language (on a 404 page: to each language's home page); a click
  stores the choice (`localStorage['slodkomi-lang']`).
- **404:** each language has its own 404 page (`/404.html`, `/en/404.html`, …); Apache serves the one matching the URL
  prefix (`public/.htaccess`). A new language needs one more `<If>` block there.
- **SEO:** `<html lang>`, a self-canonical per language, `hreflang` alternates for every language + `x-default` (Polish),
  `og:locale` + alternates, JSON-LD in the page's language, every language version in `sitemap.xml` with alternates.
  Postbuild checks reciprocity and that internal links stay in their language. Details: [SEO.md](SEO.md).
- **Not translated:** Google reviews (original words), the brand wordmark, `legalName`, the Google map (`links.mapEmbed`
  is one URL for all languages), external sites (Wolt, Instagram).
- **Analytics:** `page_view` carries `page_language` (`pl`, `en`, …); product names in `view_item` etc. stay Polish so
  reports do not split by language ([TRACKING.md](TRACKING.md)).

## Automatic language detection

An inline script in `<head>` (built in `src/components/layout/Layout.tsx`, `autoDetectScript`) runs before the first
paint when `site.i18n.autoDetect` is `true` and there is more than one language:

1. It does nothing for automated browsers (`navigator.webdriver`, e.g. Lighthouse/PageSpeed) and for bots and tools whose
   user agent matches `bot|crawl|spider|slurp|lighthouse|headless|preview|facebookexternalhit|whatsapp|telegram` — search
   engines, audits and link previews always get the URL they asked for.
2. It does nothing when the visitor has chosen a language in the switcher (`localStorage['slodkomi-lang']`) or when it
   already ran in this tab session (`sessionStorage['slodkomi-lang-checked']`). So it acts at most once per session.
3. It acts only on default-language (Polish) URLs; `/en/…` etc. are never redirected.
4. It walks `navigator.languages` and takes the first whose two-letter code is a site language; if none matches, it uses
   `fallbackLocale` (English). Polish browsers stay on `/`. Belarusian or German browsers → `/en/`.
5. If the result is not Polish it calls `location.replace()` to the same path, query and hash under the language prefix
   (`/produkt/oreo/?utm_source=x#top` → `/en/produkt/oreo/?utm_source=x#top`).

Turn it off with `"autoDetect": false`. Test it: open a private window with the browser language set to English (or
DevTools → Sensors → Locale), visit `/`; reset with `localStorage.removeItem('slodkomi-lang');
sessionStorage.clear()`.

## Adding a language

Example: German (`de`).

1. **`src/data/site.json` → `i18n.locales`:** add
   `{ "code": "de", "label": "Deutsch", "short": "DE", "htmlLang": "de", "ogLocale": "de_DE" }`. Order = order in the
   switcher. Optionally make it the `fallbackLocale`.
2. **Translations:** create `src/data/i18n/de/site.json`, `products.json` and `pages/<name>.json` for every page
   (`npm run i18n:status -- de --missing` lists every text; or `npm run ai -- "Przetłumacz wszystko na niemiecki"`).
   Set `ui.reviews.countForms` to the language's one / few / many nouns and `ui.days` to its day names.
3. **Fonts** (only if the alphabet needs it). The self-hosted fonts contain: Basic Latin + Latin-1 (`U+0000-00FF`:
   covers German, French, Spanish, Italian, Portuguese, Dutch, Scandinavian letters), the Polish letters, and the Russian
   + Ukrainian Cyrillic letters. Anything else falls back to a system font in headlines and body text. For Czech,
   Slovak, Lithuanian, Romanian, Hungarian, Turkish… add their letters; for another Cyrillic language (Belarusian `ў`,
   Serbian `ђ ј љ њ ћ џ`, Bulgarian is covered) add those; for Greek, Arabic, Hebrew, CJK pick new fonts:
   - `scripts/subset-fonts.sh`: extend the `PL`/`CYR` unicode lists (or add a new list and `pyftsubset` lines; needs
     `pip install fonttools brotli`), run `bash scripts/subset-fonts.sh`.
   - `src/styles/globals.css`: matching `@font-face` blocks with the same `unicode-range` (Anton has no Cyrillic; the
     display stand-in is Sofia Sans Extra Condensed ExtraBold under the family name `Anton` with `size-adjust: 118%`).
   - `src/components/layout/Layout.tsx`: the `CYRILLIC` list decides which pages preload the Cyrillic display font —
     add the new language code if it uses Cyrillic (be, sr, mk, bg are already listed).
   - Right-to-left languages (Arabic, Hebrew) need code: `dir="rtl"` on `<html>` and a layout review.
4. **404 page:** add an `<If "%{REQUEST_URI} =~ m#^/de/#">` block with `ErrorDocument 404 /de/404.html` and
   `ErrorDocument 403 /de/404.html` to `public/.htaccess` (copy an existing block; the build warns until it is there).
5. **Check:** `npm run content:check && npm run i18n:status && npm run build` (postbuild verifies `<html lang>`, hreflang
   and links for the new version), then look at `/de/` in `npm run dev` on a phone width.
6. **Search Console / Google Business Profile:** nothing to change; the sitemap lists the new URLs.

Removing a language: delete its entry from `i18n.locales` and its folder `src/data/i18n/<code>/` (a folder of a language
that is not configured fails validation). Old URLs then answer 404 — redirect them in `public/.htaccess` if they were
indexed.

## Translation style

- Facts only from the Polish files — never add a claim, ingredient, price or opening detail in a translation.
- Keep Polish proper names: Słodko Mi, ul. 28 Czerwca 1956 r., ul. Hetmańska, Wilda, Poznań (Russian/Ukrainian may
  transliterate the city: Познань), flavour names where they are brands (Oreo, Biscoff).
- Vocabulary bridge (from the keyword research): cynamonka = cinnamon roll = синнабон (булочка с корицей) = сінабон
  (булочка з корицею); szarlotka = apple pie; sernik = cheesecake (not сырник / сирник). Cinnabon is a trademark: write
  "синнабоны (булочки с корицей)" and never imply a link to the chain.
- Use the per-language titles, descriptions and keywords in [SEO-KEYWORDS.md](SEO-KEYWORDS.md) section 2 where they say
  exactly what the Polish content says. Titles ≤ 48 characters (the template adds " | Słodko Mi"), descriptions ≤ 155.
- Image `alt` texts are translated too (image search in each language).
- Same brand voice: warm, short, a bit playful; plain text, no HTML.
